AI Coding Agent가 코드베이스의 구조와 의도를 쉽게 이해할 수 있는 ai agent friendly, 일관되게 높은 품질의 결과물을 만들어낼 수 있도록 설계된 프레임워크

언어나 library에 묶이지 않는 재사용 framework입니다. 대상 도구는 Claude Code와 Codex입니다. repo에는 역할(implementer · reviewer)과 공통 gate만 기록하고 개인의 도구 선택은 기록하지 않습니다. 사용자는 Claude Code로 구현하고 Codex로 리뷰하지만, 팀원은 다른 조합을 쓸 수 있습니다.

codebase와 설치 · 적용 흐름은 AI agent가 읽고 실행하고 유지보수합니다. framework repo는 author가 결정할 때 로컬 Claude Code에게 수정을 맡기며, 예약된 agent loop는 없습니다. /agentive:init은 repo의 근거만 읽고 stack을 고르거나 scaffold하지 않으며 의도를 묻지 않습니다. stack은 사용자가 계획하고 자기 로컬 agent로 만듭니다. 이 페이지도 framework.yaml 한 파일에서 생성되며, 같은 내용이 페이지 안 #fw-model JSON으로 들어 있어 agent가 그대로 읽을 수 있습니다.

2026-10-27에 그동안 사용자가 정한 결정을 모두 반영했습니다. 남은 사용자 결정은 없습니다. 사람이 지켜보지 않는 실행은 헤드리스 실행(claude -p)과 Routines 실행이라고 부르고, 사람이 없다는 판정은 하나뿐입니다: 실행 명령이 넣은 AGENTIVE_HEADLESS=1, CI · GITHUB_ACTIONS, 또는 hook 입력의 permission_mode: dontAsk가 있을 때이고, 신호가 없으면 사람이 있는 실행으로 봅니다(2026-10-27 수정). .agents/manifest.yaml은 agentive manifest, package.json 같은 파일은 package 파일이라고 부릅니다.

2026-10-27 독립 검증 뒤 사용자가 다섯 가지를 정했습니다: /pr · /distill은 plugin 명령이 아니라 repo skill이라 cloud session · Routines 실행 · Codex에서도 돕니다 [7][75]. RV7은 실행으로 먼저 확인하고, 안 되면 fresh context verifier가 반박하며 다른 model은 요구하지 않습니다 [16]. reviewer 변경은 점수가 오르거나, 사람이 PR 본문에 eval-override: <이유>를 남기고 merge할 때 채택합니다 [13]. Copilot 승인은 repo 설정을 켜면 필수 승인을 채우므로 init이 끄라고 안내합니다 [94][155]. 사람이 없다는 신호에서 CLAUDE_CODE_REMOTE를 뺐습니다 [24].

각 요소에는 공식 (공식 문서에서 확인, 출처 번호 표시), 설계 (설계 제안), 미정 (아직 정하지 않음) 태그가 붙습니다. 결정이 필요한 항목은 모호한 부분에서, 문서로 확인하지 못한 사실은 미검증 사실에서 봅니다. 리뷰가 어떤 단계로 merge 결정까지 가는지는 코드 리뷰 pipeline에, chain 진입 판단 intent.md 필요?가 yes인 작업이 intent.md → spec.md → plan.md를 거쳐 사람 승인을 받는 흐름은 spec 단계 artifact chain에 있습니다.

영역별 역할

Z1 · Framework repo

단일 원본 설계

framework.yaml 원본에서 generator가 Claude Code plugin과 Codex용 repo layer 출력, 그리고 이 지도를 만듭니다. framework repo는 author가 결정할 때 로컬 Claude Code에게 파일 수정을 맡겨 유지하며, 예약되거나 자율적인 agent loop는 없습니다 (사용자 결정 2026-10-14).

루트 AGENTS.md(CLAUDE.md가 @AGENTS.md로 가져옴 [5])에 수정 규칙을 명령형으로 적습니다 [49]: 원본과 schema 위치, 돌릴 generator, 돌릴 self-test, changeset으로 version과 CHANGELOG를 올리는 법, author 확인이 필요한 범위(U3). self-test(generate --check, schema 검증, fixtures 4종 F2)는 framework를 고칠 때만 로컬 commit 전과 CI의 pull_request에서 돌립니다 [48]. fixtures 4종에서는 LLM 없는 결정적 init · 적용 시험(생성 파일, 다시 돌려도 그대로, 기존 파일 보존)을 매번 돌리고, agent가 실행하는 fixture task는 init · 적용 관련 경로가 바뀔 때만 1–2개 stack에서 돌립니다 (사용자 결정 2026-10-27, OpenSpec · BMAD 선례 [133][134]). version은 changeset 파일로 올리고 두 plugin manifest에 같이 반영합니다 (F4) [50]. compat.yaml도 여기에 있습니다.

Z2 · Distribution

공식 marketplace로 배포 공식

Claude Code는 .claude-plugin/marketplace.json 카탈로그로 plugin을 배포합니다 [1]. third-party marketplace의 auto-update는 기본 off라서 갱신은 claude plugin update로 하고, 이어서 /agentive:update를 실행해 repo layer를 새 template에 맞춥니다 [18].

Codex는 .agents/plugins/marketplace.json과 root plugin.json을 쓰고, agent가 실행할 수 있는 명령은 codex plugin marketplace add|upgrade까지입니다. 설치는 plugin browser에서 사람이 하고 [14], IDE extension은 plugin을 지원하지 않으며 [15], plugin hooks는 자동 trust되지 않습니다 [11]. 그래서 Codex 기본값은 repo layer만 쓰는 것입니다 (D13).

Z3 · Plugin layer

모든 project가 공유하는 도구 설계

/agentive:init(처음 한 번) · /agentive:update(이미 init한 project 갱신) · /agentive:reprove · SessionStart hook. slot을 도출하는 derive-<slot> 단계는 이 명령들 안의 script이고 따로 부르는 skill이 아닙니다. /pr · /distill은 cloud session · Routines 실행 · Codex에서도 돌도록 repo skill로 옮겼습니다(사용자 결정 2026-10-27, Z4) [7][75]. init과 update는 hooks · permissions · CI를 쓰므로 사용자 호출 전용(disable-model-invocation: true, Codex allow_implicit_invocation: false)이고, 파일을 쓰기만 하며 commit하지 않습니다. /agentive:reprove와 repo skill /pr · /distill은 agent도 부를 수 있고(disable-model-invocation: false를 명시) 결과는 PR · review pipeline · CI를 거칩니다 (사용자 결정 2026-10-27). init은 repo의 근거만 읽고 stack을 고르지 않으며 scaffold하지 않고 의도를 묻지 않습니다. 빈 디렉터리에서도 실패하지 않고 stack slot을 '근거 없음 · 대기'로 둡니다. 이미 설정된 repo에서 init은 멈추고 읽기 전용 update --status를 보여 준 뒤 update를 안내하며, update는 agentive manifest가 없는 repo에서 멈추고 init을 안내합니다. init이 묻는 질문은 REVIEW.md 복사본 예/아니오 하나이고 --managed-review-copy · --no-managed-review-copy로 묻지 않고 정합니다. U2 범위 파일(hooks · permissions · CI · .claude/settings.json · .codex/ · review 설정)은 쓰기 전에 사람이 확인하고, 사람이 없는 실행이면 건너뛰고 pending-confirmation에 남겨 다음 대화형 세션이 알립니다. Claude Code는 명령 뒤 인자를 $ARGUMENTS로 넘기고 [2], Codex의 skill 인자 전달 방식은 문서에 없습니다(UV-23). cloud session은 user plugin도, repo의 enabledPlugins도 load하지 않으므로 공식 [7][18], 이 영역만으로는 guardrail이 되지 않습니다.

Z4 · Repo layer

project에 commit되는 계약 설계

지침 파일, agentive manifest(.agents/manifest.yaml)의 slot, decisions.yaml, rubric(.agents/rubric.yaml), 명령 규칙(.agents/guard.yaml), rule pack, verify · precommit-review skill, chain 단계마다 repo skill 하나(/chain-intent · /chain-spec · /chain-plan <slug>, 각자 확인 script), PR을 여는 skill /pr, 학습 PR skill /distill(2026-10-27 plugin에서 옮김), 열린 PR 후속 처리 skill /pr-feedback, reviewer 정의 .agents/agents/<reviewer_id>.md, .agents/bin/verb · .agents/bin/agentive-lint, hooks · permissions · sandbox(generated · vendor 경로는 Read와 함께 Edit도 deny, Edit 규칙이 Write 도구까지 막음 [6]), Codex hooks · rules · config, CI · branch protection(repo에 secret scanner 설정이 있으면 verify verb에 연결하고, init이 push protection 안내 한 줄을 냅니다 [143]), review 기준 파일, ADR, docs/plans/<slug>/(intent.md · spec.md · plan.md). 각 파일의 형식은 기계판독 계약의 JSON Schema를 따릅니다. GitHub Free private repo에서는 branch protection · CODEOWNERS를 쓸 수 없고(개인 Pro 또는 조직 Team 이상 필요 [33][84]) dependency review는 조직 Team + Code Security가 필요해 init이 강제하지 못하는 부분을 보고합니다 [85].

설계 생성 파일은 framework 소유입니다. manifest.generated가 렌더링 결과의 sha256을 기록하고, update에서 hash가 다른 파일은 사용자가 수정한 파일로 보아 보존하고 drift로 보고하며 --force만 덮어씁니다. 이 방식은 spec-kit의 파일별 sha256 manifest를 따릅니다 [63]. 사용자도 고치는 공유 파일(AGENTS.md · CLAUDE.md · code_review.md · .gitignore)에서는 framework가 명시적 START/END marker 사이(managed region)에만 쓰고 바깥은 건드리지 않습니다. region 안에는 마지막 검증 날짜와 commit SHA가 있고, update가 그 SHA 이후의 삭제 · 이름 변경(git log --diff-filter=DR)으로 낡은 줄을 찾습니다 [66][67]. region 본문도 같은 sha256 baseline으로 비교해, 사용자가 region 안을 고치면 보존하고 drift로 보고하며 --force만 덮어씁니다. JSON 파일은 marker를 둘 수 없어 전체 파일 baseline을 씁니다. 사용자가 생성 파일을 바꾸고 싶으면 .agents/custom/(commit되는 사용자 소유 폴더, init · update가 쓰지 않음)에 같은 상대 경로로 sparse override 파일을 둡니다. 병합은 scalar는 override 우선, mapping은 deep merge, id가 모두 있는 목록은 id로 병합, 그 밖의 목록은 base 뒤에 append이고 삭제는 못 합니다 (BMAD 규칙 [60], 생성 파일 형식에 쓰는 것은 확장 UV-24). gitignore되는 개인 layer는 없습니다. 생성 파일이 commit되므로 개인 layer가 있으면 같은 commit이 머신마다 달라집니다. CI drift 검사는 없습니다.

review 기준 파일: 리뷰어마다 읽는 파일이 다릅니다. 관리형 Code Review(2026-10-15 GA [91])는 REVIEW.md를 읽고 로컬 · CI /code-review는 읽지 않습니다 [16]. Codex는 AGENTS.md에서 참조한 code_review.md를 따를 수 있습니다 [12]. 사용자가 U4 = C로 정했습니다: 기준은 code_review.md 하나이고 AGENTS.md가 참조하며, Claude Code는 import로 [5], Codex는 경로 참조로 읽습니다. REVIEW.md 복사본은 관리형 Code Review를 쓰는 팀을 위한 opt-in입니다. init이 만들지 묻고(기본 아니요) 답을 review.managed_code_review_copy에 저장하며, update는 묻지 않고 그 값을 따릅니다. 기준 파일은 변경 파일의 상위 폴더에 있는 것만 적용합니다. CLAUDE.md와 AGENTS.md는 code_review.md가 적용되지 않는 변경 파일에만 fallback이고, 한 파일을 둘 다로 평가하지 않으며, 적용되는 기준 파일이 없으면 정상 결과입니다.

Z5 · Work loop

역할 기반: implementer → verify → reviewer → CI floor → merge 설계

편집마다 lint, 턴 종료마다 inner verify를 돌리고, Stop hook이 자체 counter로 cap N까지 차단합니다 [3][4]. 진전이 없으면 branch별 handoff를 남기고 한 번만 이어 갑니다. 모든 verb는 .agents/bin/verb로 실행해 실패 요약과 다음 읽기 명령 한 줄만 context에 남깁니다. 위험한 명령은 .agents/guard.yaml이 deny하거나 사람에게 묻고, 사람이 없는 실행이면 deny하고 handoff합니다. chain 진입 판단 intent.md 필요?가 yes인 작업은 spec 단계 artifact chain을 따릅니다(agent가 한 줄로 알리고 /chain-intent로 한 턴에 질문 하나씩 묻고, 사용자 지시가 양방향으로 우선): intent.md(intent PR merge = 승인) → spec.md(spec PR merge = 수락) → 읽기 전용 계획 모드에서 사람이 승인한 plan.md(feature branch 첫 commit) → slice마다 commit. 다음 단계는 이전 artifact가 기본 branch에 있을 때만 script가 엽니다. implementer와 reviewer는 다른 context여야 하며(필수), 가능하면 다른 도구 · model을 씁니다(권장). 리뷰는 코드 리뷰 pipeline을 따르고 merge 판정은 RV8 script가 내립니다. 자동 merge는 U1 = C: tier 0 자동, tier 1은 RV7b 28점 이하이고 shadow mode를 지난 뒤 자동, tier 2는 지시한 사람이 직접 merge하고, 그 사람이 한눈에 판단하도록 PR body 맨 앞에 ## Explainer(설명 + 기존 · 이후 workflow 흐름도)가 반드시 있습니다(tier 2 Explainer 예시). 같은 tier · 출처의 자동 merge PR이 7일 안에 revert · hotfix를 2건 받으면 그 범위만 멈춥니다. PR이 열린 뒤 남은 thread와 실패 check는 repo skill /pr-feedback이 한 번에 한 번씩 처리합니다: 고치고 push 1회, finding마다 agentive-reply: 답글 줄, 고치지 않은 사람 thread는 열어 둠, merge는 하지 않음. 확정된 important finding에 수정 대신 이유로 답하면 사람이 merge합니다(finding_disputed).

Z6 · Maintenance

사람 대신 agent가 돌리는 유지보수 설계

FileChanged로 slot 재증명, SessionEnd가 queue에 남긴 trace를 /distill이 나중에 정리 공식 event [3]: 반복 실수를 분류해 가장 싼 결정적 check(기존 check 연결 → linter 설정 → test → guard.yaml → .agents/checks/)로 옮기고, 실패 재현과 통과를 증명한 PR만 열며, 그 PR은 항상 tier 2입니다. distill은 리뷰 noise(같은 reviewer · bug class가 merge된 PR 2개 이상에서 wrong · intentional · not_important로 답해짐)를 code_review.md의 ## Do not report 근거 요구 한 줄 등으로, 놓친 버그(revert · hotfix)는 Claude Code 팀처럼 reviewer 앞에 없던 지식 · skill · check로 옮기고 reviewer eval 양성 case 초안도 만듭니다 [89][146]. janitor(기본 off, kind별 열린 PR 하나, 항상 tier 2), /doctor prompt-audit(새 model 채택 때 사람이 실행) 공식 [5], /agentive:update(plugin 갱신 뒤 repo layer 재적용, commit 없음), reviewer eval set(리뷰어 프롬프트·모델·도구·규칙 변경 PR에서 CI가 전후를 3회씩 돌려 PR 댓글로 올리고, 점수가 오르면 사람이 채택하고 오르지 않으면 PR 본문에 eval-override: <이유>를 남길 때만 채택, 예약 실행 없음) [89][137][13], skills.lock · dependency-review 공급망 검사, branch별 handoff. metrics 파일은 없고 kill switch 개수만 gate가 그때 셉니다. 이 영역은 user project 안의 유지보수이고 framework repo 자체에는 예약된 agent가 없습니다.

spec 단계: intent.md → spec.md → plan.md artifact chain (Z5)

사용자 결정 2026-10-27 작업 시작 때 chain 진입 판단 intent.md 필요?가 yes인 작업은 공식 AI-native SDLC의 artifact chain을 따릅니다 [13]. 사용자는 평소 말로 요청하면 되고, agent가 한 줄로 알린 뒤 /chain-intent로 한 턴에 질문 하나씩 묻습니다. docs/plans/<slug>/에 intent.md → spec.md → plan.md 순서로 쓰고, 단계 사이마다 사람이 승인합니다: intent PR merge, spec PR merge, 읽기 전용 계획 모드에서의 plan 승인. 승인된 artifact가 기본 branch에 있어야 다음 단계가 시작되고, 이 확인은 git으로 하는 script입니다. 아래 그림은 누가(agent · script · CI · 사람) 각 단계를 맡는지 세 영역으로 나눠 보여 줍니다.

Stop hook 설계
verify.json의 실패 수와 stop.json counter로 DONE · PENDING · NO-PROGRESS · CAP을 결정합니다. NO-PROGRESS면 branch별 handoff 파일을 쓰고 한 번만 이어 가며, 다음 Stop은 handoff_requested로 판정해 verify를 다시 돌리지 않습니다. counter는 verify 통과 · 실패 감소 · 새 시작 · NO-PROGRESS 직후에 초기화하고, UserPromptSubmit에서는 초기화하지 않습니다(사람 입력인지 구분할 필드가 없음 [3]). stop_hook_active만으로 통과시키지 않습니다. 공식 cap(도구 호출 없이 연속 8회)은 백업입니다 [4].

리뷰 수렴
round 1은 전체 diff, round 2부터는 마지막으로 본 head 이후의 diff와 열린 finding만 봅니다. 전체를 다시 보려면 agentive:full-review 라벨을 붙입니다 설계 판단. 이미 게시한 finding은 다시 올리지 않고, 이유를 적어 답한 thread(agentive-reply: 줄이나 추론한 이유)는 존중합니다. 차단 finding마다 수정이나 이유 있는 답글이 있어야 합니다. 3 round 뒤에도 차단 finding이 남으면 reviewer가 접근 방식을 다시 생각하라고 하고 사람에게 넘깁니다 [89].
reviewer eval set
agentive에 남은 eval은 이것 하나입니다(일반 implementer eval은 2026-10-27 삭제). 양성 case는 사고를 내거나 버그를 놓친 PR이고, 정답 위치 file:line(허용 범위)을 사람이 확인합니다(case를 넣는 tier 2 PR의 merge). 출처는 fix PR · revert · 재현 diff · 주입한 버그 + 사람 확인 중 하나입니다 [135][136]. 음성 case는 문제없다고 알려진 PR과 안전한 반례이고, 전에 wrong · intentional로 답한 위치를 forbidden_findings로 둘 수 있습니다. evals/reviewer/<id>.yaml(reviewer-eval-case.schema.json)에 두고, distill이 revert · hotfix와 리뷰 noise에서 초안을 만듭니다. 리뷰어 프롬프트·모델·도구·규칙 변경 PR에서 CI가 전후를 3회씩 재채점해 결과와 상관없이 PR 댓글로 올립니다. 점수가 오르면 사람이 tier 2로 merge해 채택하고, 오르지 않으면 PR 본문에 eval-override: <이유> 한 줄을 남길 때만 merge합니다(사용자 결정 2026-10-27, 이전의 '오를 때만'을 바꿈) [13]. 매일 · 예약 실행은 없습니다(공식 자료와 다른 사용자 결정 [89]). 점수: 게시될 important finding이 기대 위치에 있어야 잡은 것(요약 언급 제외), 비교는 양성 먼저 · 같으면 음성의 원치 않는 finding이 적은 쪽, 전에 잡던 것을 놓치면(newly_missed) 채택을 권하지 않음, '개선'은 실행 간 흔들림보다 큰 향상이거나 퇴보한 case가 없을 때입니다 설계 판단 [137]. 답글 이유(fixed · wrong · intentional · not_important) 집계는 gh api 조회로 하고 파일로 남기지 않습니다 [89].
리뷰 noise · 놓친 버그
/distill이 agentive-reply: 이유를 gh api로 읽어, 같은 reviewer · bug class가 merge된 PR 2개 이상에서 noise로 답해지면 tier 2 PR을 엽니다(agent 초안, 사람 merge) 설계 판단. CI가 이미 잡는 것 · generated 경로는 RV1 제외나 기존 check, wrong은 code_review.md ## Do not report의 근거 요구 한 줄, not_important는 'near-certain and severe일 때만' 한 줄, intentional은 code comment나 ADR [146]. 새 줄보다 기존 줄을 좁히고 [147], RV2 신뢰 경계와 겹치는 줄은 쓰지 않으며, origin PR에서 noise가 사라지고 전체 reviewer eval이 newly_missed 없음일 때만 엽니다. revert · hotfix된 놓친 버그는 Claude Code 팀처럼 reviewer 앞에 없던 지식 · skill · check로 옮기고(## Always check 줄이 아님) reviewer eval 양성 case 초안도 만듭니다 [89]. REVIEW.md 복사본이 꺼져 있으면 관리형 Code Review는 code_review.md를 읽지 않습니다 [146].

적용 흐름과 강제 계층

framework를 설치하고 project에 처음 적용하는 순서(0–5단계)와, 이미 init한 project를 갱신하는 단계(6단계)입니다. init은 repo 근거만 읽고 stack을 고르거나 scaffold하지 않으며, 빈 디렉터리에서도 실패하지 않습니다. init과 update는 파일을 쓰기만 하고 commit하지 않으며, U2 범위 파일만 쓰기 전에 사람이 확인합니다. 아래 패널은 init 규칙, 어떤 장치가 실제로 강제하는지(guard.yaml · sandbox · branch protection), 언제 멈추고 무엇을 넘기는지(handoff), context를 어떻게 아끼는지를 정리했습니다.

init이 repo를 어떻게 다루는지에 관한 규칙입니다. 근거가 되는 공개 repo 파일은 출처 번호로 적었습니다.

GF · 빈 디렉터리근거가 없어도 실패하지 않습니다. stack과 무관한 뼈대만 쓰고 stack slot은 '근거 없음 · 대기'로 표시합니다. 명령을 추측하지 않고, repo에 적힌 stack은 명령이 아닌 TODO로 남깁니다 [67].

NP · 미리보기 없음 · commit 없음dry-run · diff 승인 단계를 두지 않습니다. init과 update는 파일을 쓰기만 하고 commit하지 않으며 바뀐 파일 목록을 보고합니다(선례 다수: init 6/9, update 5/5). U2 범위 파일만 쓰기 전에 사람이 확인합니다.
